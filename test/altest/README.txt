Проверка приёмов работы со звуком на настоящих библиотеках игры.

Зачем: патч синхронизации музыки трогает источник OpenAL, и надо знать,
какие приёмы вообще работают с тем звуком, который использует игра.
Программа игру не запускает, она берёт OpenAL32.dll и ALURE32.dll рядом
с собой и повторяет на них наши действия.

Сборка (Linux, кросс-компилятор):
    i686-w64-mingw32-gcc -O2 -o altest.exe altest.c

Запуск: положить рядом библиотеки игры и трек, затем
    wine altest.exe music.mp3
или на Windows просто altest.exe music.mp3

Программы:
    altest.c   пять приёмов работы со звуком
    offset.c   через сколько после запуска сдвигается позиция источника
    latency.c  умеет ли библиотека сообщать задержку вывода
    findfn.c   поиск функции в библиотеке так, как это будет делать патч

Что проверяется в altest.c:
    1. перемотка и запуск, тем же приёмом игра зацикливает трек
    2. задание позиции играющему источнику
    3. приглушение и возврат звука
    4. отложенный запуск: источник заряжен, но не пущен
    5. пауза средствами ALURE из другого потока

Результат прогона на библиотеках игры:

    все пять приёмов работают, ошибок OpenAL нет
    позиция источника сдвигается через 8-9 мс, задержку устройства не отражает
    расширение AL_SOFT_source_latency поддерживается и сообщает задержку вывода
    поиск функции по таблице имён находит тот же адрес, что и Windows

Последнее и есть основа для настоящей синхронизации: патч не может звать
GetProcAddress, потому что игра её не импортирует, зато у него есть адрес любой
функции OpenAL из таблицы импорта игры. От него ищется начало библиотеки
шагами по 64 КБ вниз до заголовка, дальше читается таблица имён.
